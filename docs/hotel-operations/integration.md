# 接入、权限预检与现场联调

## 1. 本轮已经核实的技术事实

以下结论来自仓库与固定依赖 `openclaw@2026.4.1` 的实际源码，不推断其他版本具有相同行为。

| 已核实内容 | 对实施的影响 |
| --- | --- |
| ClawX 的 `@agent` 切换目标 Agent 的独立会话 | 总管调度需使用持久任务与实际 Gateway 调用，不能用 `@agent` 冒充转发 |
| `chat.send` 接受 `sessionKey`、`message`、`deliver`、`idempotencyKey` 等字段，不接受每次运行的 `tools` / `sandbox` 覆盖；Schema 禁止额外字段 | 派单前核验 Agent 的实际配置，不能随意构造一个 `readOnly:true` 参数 |
| `deliver:false` 只影响回复投递 | 不等于关闭浏览器、命令、付款或消息工具 |
| `chat` 事件经 Main 转为 `chat:message`，其 payload 在 `message` 中；`agent` 事件走另一条 notification 路径 | 结果只认匹配会话/运行号的 assistant 回传；避免把双通道通知重复当完成 |
| `chat.send` 超时可能发生在 Gateway 已接收之后 | 保留执行记录，读取原会话核对，不立即重新发送 |
| 工具策略按 profile、provider、global、agent 及 sandbox 逐步过滤 | 显式 Agent allowlist 可作为工具上限，其余策略还会进一步限制 |
| Agent 的 `alsoAllow` 会与 `allow` 合并 | 检查时必须一并核验，不能只看 `allow` |
| 仅含插件或当前不可用工具的 allowlist 可能被 OpenClaw 忽略 | 清单要含稳定存在的核心工具，不接受“一个未知只读插件名”作为隔离证明 |
| `session_status` 还能设置会话模型覆盖 | 本项目不把它自动归为纯只读工具 |
| ACP / CLI 后端具有自己的执行权限体系 | 本地嵌入式工具配置不能证明独立 Codex/CLI 执行器已隔离 |

对应实现入口：[`execution-policy.ts`](../../electron/services/hotel/execution-policy.ts)、[`runtime.ts`](../../electron/services/hotel/runtime.ts)、[`gateway-payload.ts`](../../electron/services/hotel/gateway-payload.ts)。升级 OpenClaw 后要重新检查协议和权限语义；版本不符时默认不派单。

## 2. 复用现有 Agent 的检查步骤

先按[运营电脑本地 Codex 交接单](onsite-handoff.md)只读确认实际电脑、应用与 Gateway 来源、配置目录和登录状态，再保留本地恢复副本。正常启动有既有同步副作用，同一应用换安装目录不隔离数据；不要把历史登录反馈当成当前连接，也不要要求用户把令牌发到聊天。交接单固定了已验证功能提交，并区分 Windows 手动打包与带发布动作的 macOS Release 路径。

先记录实际 Agent ID、模型、工作区、账号与工具权限，再在工作台绑定。`enabled` 是本地老板允许派单的开关，不会创建沙箱、缩小账号权限或修改既有 Agent 配置。

查询/分析任务的预检要求：

- 显式配置 `agents.list[].tools.allow`，不得为空或含通配符、工具组以及未核验插件名。
- `alsoAllow` 也必须处于受限清单内。
- 可接受的工具上限为 `read`、`web_search`、`web_fetch`、`sessions_list`、`sessions_history`、`agents_list`、`memory_search`、`memory_get`。
- 至少包含一个稳定核心工具：`read`、`sessions_list`、`sessions_history`、`agents_list`。
- 使用 `read` 时，生效的 `tools.fs.workspaceOnly` 必须为 `true`。
- 模型及回退模型必须可解析，不能使用未经此检查器核验的 ACP / CLI 执行路径。

下面只是供现有配置合并审核的片段，不是可覆盖整份配置的文件：

```json
{
  "id": "existing-agent-id",
  "tools": {
    "allow": ["read", "web_search", "web_fetch"],
    "fs": { "workspaceOnly": true }
  }
}
```

保留已有模型、技能、身份和工作区。若该 Agent 还承担需要浏览器或命令执行的其他工作，不应为满足检查直接删除它的能力。可先使用受限执行岗位，或将后台导出的必要汇总报表放入可访问工作区，再执行分析。专用平台只读适配器需要完成行为验证后才能加入受信范围。

预检返回 `verifiedTools` 表示核实的**工具上限**，不代表每个工具都已配置 API Key 或可实际调用。它也不证明已连接的外部 Gateway、运行中的配置、第三方插件代码与本地文件完全一致；现场应确认 Gateway 使用本项目对应运行时、已重载当前配置，并完成一次小任务联调。

### 隔离代码任务

`code` 任务只分配给技术岗，工具上限可增加 `write`、`edit`、`apply_patch`、`exec`、`process`，并要求：

1. 所有会话使用 Docker 沙箱，`mode:"all"`，scope 为 `session` 或 `agent`。
2. Docker 网络为 `none`、根文件系统只读、drop 所有 capabilities，没有额外宿主机挂载或绕过隔离选项。
3. `tools.exec.host` 明确为 `sandbox`；`auto` 不是隔离证明。
4. 显式关闭 elevated，文件工具限定工作区。
5. 工作区是适合该技术任务的隔离开发目录。现场验证 Docker 可用、源码与依赖可访问后才能把一次技术任务视为可运行。

配置预检通过不代表镜像、依赖或 Docker 服务可用。沙箱启动失败应回传真实错误，不能降级到宿主机执行。技术工单的创建、交接与回传功能仍保留，不会因为尚未接通 Codex 而丢掉问题记录。

## 3. MCP 桥接：本机客户端

本实现提供独立于 Gateway / Host API 管理令牌的酒店桥接令牌。授权按门店限定，默认只提供读取与建立草稿；可以单独开启派单权限，轮换和撤销立即使旧令牌失效。

1. 在“酒店总管 → 接入与门店 → ChatGPT 与 Codex 桥接”选择授权门店。
2. 根据用途决定是否允许派单，启用桥接后保存一次性显示的令牌到客户端本地凭据配置。
3. 对支持 stdio MCP 的本机客户端，设置启动命令为 `node`，参数为本仓库 `scripts/hotel-mcp-bridge.mjs` 的实际绝对路径。
4. 为这个子进程提供环境变量 `CLAWX_HOTEL_BRIDGE_TOKEN`。如果应用改过 Host API 端口，再提供对应的 `CLAWX_PORT_CLAWX_HOST_API`。
5. 先执行 MCP `initialize` / `tools/list`，再读授权门店的 `hotel_status`。确认跨店请求被拒绝后，用一项草稿任务测试交接。

不要用 Gateway Token 或 Host API Token 替代酒店桥接令牌；不要把原始令牌放入聊天正文、知识库、公开仓库或命令历史。桥接只监听本机回环地址，脚本没有任意 URL 转发参数。

### MCP 工具权限

| 工具 | 默认授权 | 开启派单后 | 作用 |
| --- | --- | --- | --- |
| `hotel_status` | 可用 | 可用 | 同店任务、知识、计划与审计 |
| `hotel_report` | 可用 | 可用 | 有源、已验收的经营日报 |
| `hotel_create_task` | 可用 | 可用 | 建立幂等草稿；不自动执行 |
| `hotel_queue_task` | 不提供 | 可用 | 将查询、分析或隔离代码任务入队 |
| `hotel_dispatch_task` | 不提供 | 可用 | 请求 Main 检查依赖、岗位、权限后派发 |
| `hotel_submit_result` | 不提供 | 可用 | 只回传普通业务任务的当前执行批次；拒绝 `supervisor` 岗位和所有带 `reviewTarget` 的任务 |
| `hotel_reconcile_task` | 不提供 | 可用 | 读取原会话并核对结果；不重发任务 |
| 老板审批、岗位权限、支付/退款/发布 | 不提供 | 不提供 | 不能通过此桥接获取 |

此桥接是无状态 MCP JSON-RPC POST 接口，协议版本为 `2025-06-18`，不提供 SSE stream。本机脚本将逐行 stdio 消息转为该 POST 接口。客户端兼容性仍需实际验证。

桥接回传会记为 `resultOrigin:"bridge"` 并保留在结果历史中，不授予验收成功。总管讨论结果通过对应 Gateway 会话返回；独立验收结果还必须匹配服务端固定的 `reviewTarget`。共享桥接令牌没有老板验收或批准能力。

### 远程 ChatGPT 连接

云端 ChatGPT 无法直接访问另一台电脑的 `127.0.0.1`。本机 MCP 脚本写好或令牌生成，都不表示当前聊天已经连通。

远程接入需要一个客户端支持的、经身份验证的 HTTPS MCP 接入层，限定门店和工具，处理凭据生命周期，并验证实际返回结果。该远程接入层不包含在本分支；不应把整个 ClawX Host API 或本地 Gateway 端口直接开放到公网。远程接入前，本机工作台、任务协议与本机兼容客户端已经可以作为交接入口。

## 4. 酒店后台现场检查

| 系统 | 必须检查 | 通过证据 | 尚未接通时 |
| --- | --- | --- | --- |
| 别样红 | 当前门店、登录有效性、只读范围、经营日、可售/已售房与房费口径 | 实际查询或合法导出、采集时间、字段定义 | 导入任务输入所需的汇总报表；显示缺数，不填写 0 |
| 携程 | 店铺归属、账号权限、曝光/点击/订单/评价实际可获得字段 | 同统计期来源、指标分母与页面/导出标识 | 只分析已给定字段，缺失指标列出 |
| 抖音 | 创作资料、素材使用范围、真实房型/服务信息、同店内容历史与效果来源 | 制作方案及评分理由；复用后独立审核；人工发布 URL；效果结论需实际指标 | 已提供历史轮换、质量模板和新草稿复用；未接平台时不宣称有播放/转化数据或自动发布 |
| 竞对 | 兴城市目标酒店、入住日、人数、房型、税费、早餐和退改条件 | 实际可比报价、来源与采集时间 | 候选酒店与已查实价格分开，不伪造实时价 |
| 财务 | 汇总数据范围、退款、平台结算、佣金、经营日与到账日 | 可追溯的脱敏核对依据 | 保留差异与待补凭据，禁止猜测差额原因 |
| 客服 | 评价/投诉来源、处理负责人、授权范围与服务政策 | 工单和回复草稿、处理跟踪 | 不自动联系客人或承诺补偿 |

现场登录、验证码和设备授权属于实际运营电脑上的步骤。历史对话中“已经登录”只能作为线索，不能记为本次接通结果。

## 5. 联调验收顺序

### A. 不调用酒店后台的完整任务链

创建一条已授权的脱敏知识，绑定受限分析 Agent，建立任务并入队。确认产生独立会话与执行批次；Agent 返回匹配任务/批次的 JSON；结果先到待验收，验收后才进入日报或父任务依据。关闭并重开应用，确认记录仍在。

分别录入本店的 `property`、`rooms`、`policy`、`metrics` 基础知识，建立未显式勾选知识的任务，核对派单说明仍包含这些条目的最新版本和来源。另一个门店的知识不应出现；显式引用其他类别时应同时带入。

### B. 多岗位与总管

创建联合日报或定价调查。检查子任务有各自岗位和独立会话；让一个子任务返回缺项，确认父任务不能越过该缺项宣称全体完成。补全并验收后再汇总。

另建总管讨论任务，回传含 `plannedTasks` 的方案，预览后确认派单；检查子任务和依赖原子建立、重复点击不重复建单，最终总管汇总仍引用原讨论与已验收结果。自由聊天文本中的“已派单”不作为证据。

启用不同 Agent ID 的总管，检查独立验收能通过或退回固定版本结果；更换绑定、修改原结果后旧验收应失效。总管不能自审，外部桥接不能通过伪造 `assessment` 绕过验收，经营变更审批仍由老板操作。

用获准派单的桥接客户端分别尝试向普通总管任务和带 `reviewTarget` 的任务调用 `hotel_submit_result`，两者都应拒绝。普通业务结果则保留 `bridge` 来源，交后续独立验收。

### C. 失败、重启和取消

使用可控的测试网关或故障条件验证：发送回执超时、执行中重启、格式不合法、旧 attempt 回传和重复完成通知。确认只核对旧会话、不盲目重发，过期回传不能覆盖新结果。取消请求同时尝试 `chat.abort`，不能把“本地标记取消”当成对远端已停止的证明。

### D. 审批边界

建立具体变更计划，批准后核查版本与摘要。修改方案后旧批准必须失效。当前无生产执行适配器，因此任何批准都不得触发后台写入，也不得显示“已调价/已付款”。外部 MCP 客户端不能批准自己的计划。

在详情及同店导出中核对 `planHistory` 保留旧方案及批准范围，`resultHistory` 保留各次回传、来源、完整证据及验收意见。修改、退回或重跑后，旧证据可查，但不能套用于当前新版本。

### E. 抖音质量与发布边界

分别回传 79 分与 80 分的完整样例，核查低分内容必须有优化建议，且不能登记发布。即使高分，未经验收也不能登记；Agent 提交 `publication` 应被拒绝。人工登记链接仅记录已发生的人工操作。

连续建立同店内容任务，核对派单包含历史选题与下一主题建议，自动参考模板仅选已验收且达到 80 分的结果。通过“复用已验收内容”建立新草稿，确认旧评分、批准和发布记录没有继承；新资料修改后应重新制作并验收。另店内容不得进入本店历史、模板或复用任务。没有平台效果数据时，不得把高质量模板标为高播放或高转化模板。

### F. 多店和定时计划

建立另一个测试门店，核查任务、知识、依赖、导出和桥接凭据不能越店。新计划默认暂停；确认时区、开启后验证同一时段只生成一个任务，离线多日不自动追跑旧任务。只运行本机计划，不复制或更改用户已有 ChatGPT 简报、邮件监控计划。

### G. 两个经营日的对比

准备两个不同、已结束的完整经营日报告，使用同店、同时区、相同口径及日界线的已验收指标，核对差值和相对变化。缺数据、口径不一致、部分经营日或尚未结束时应显示不可比原因；基期为 0 时不计算比例。这里只验收数字比较和条件检查，不把前后差值当作策略的因果效果。

## 6. 分阶段落地与完成定义

| 阶段 | 本阶段完成条件 |
| --- | --- |
| 代码与工作台 | 核心测试、权限测试、通信回放、类型检查及 UI 验证通过；功能和限制在文档可查 |
| 现场任务闭环 | 在运营电脑完成真实 Agent 的派单、回传、验收、重启恢复与一项脱敏数据分析 |
| 酒店只读接入 | 别样红、携程、竞对、财务及客服逐项有当前可验证来源；日报无虚构数据 |
| 三平台交接 | 实际 MCP 客户端可以读/建任务；远程 ChatGPT 如需接入，完成真实的认证和端到端联调 |
| 经营写入 | 每个生产适配器完成对象范围、审批绑定、幂等、回执、异常及回退测试后，才能另行启用 |
| 连锁复用 | 复制岗位与模板，同时保持各门店账号、经营日、房型和数据范围独立 |

生产适配器、远程连接、账号和素材不能只靠代码猜测补齐。保留对应岗位、协议和待办，逐项完成真实接入；“已实现代码”“已部署”“已接通”“已验收”分别记录。
